About me

I'm a software engineer working on eBPF-based observability for cloud clusters at Sedai. It means instrumenting entire clusters without becoming the overhead it's meant to measure. Before Sedai I was at Juniper Networks, working on Contrail, their network management and cloud automation platform, where I helped build features like MAC-IP learning and BGP-as-a-service.

Work aside, I really enjoy low-level systems and GPUs. I ran a study of how CNN inference actually runs on a GPU, carrying it from a naive CUDA kernel all the way to a production TensorRT engine and picking up cuBLAS, kernel fusion, and FP16 along the way. I also used LLMs to optimize low-level cache replacement policies as the final project for my Generative AI class.

Right now I'm building an XDP-based load balancer, pushing L4 balancing down into the kernel with XDP and chasing throughput at the lowest level.

And for fun there's PawnHub, a C++ chess engine that's crossed ~1800 Elo, with a transposition table, Zobrist hashing, and search heuristics behind a UCI interface.

accelerating-cnn

Every way a CNN's forward pass gets run on an NVIDIA GPU, from a naive CUDA kernel to a production TensorRT engine. Built from scratch, checked against a CPU reference, and profiled to explain which approach wins in which regime, and why.

  • No single winner. At one channel my tiled kernel beats cuDNN; by 64 channels cuDNN is ~25× faster. It depends on the shape of the problem.
  • Reformulate, don't micro-optimize. Turning the convolution into a matrix multiply (im2col + cuBLAS) beat every hand-tuned direct kernel, ~10× over naive.
  • FP16 isn't free speed. It only helps when the Tensor Cores engage: 5× in TensorRT, sometimes slower than FP32 in raw cuDNN.
